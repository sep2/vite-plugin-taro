vpt全自动分包让你只需要关心功能何时加载。你不再需要手动决定模块应放入主包还是某个分包，也不需要按体积反复调整分包目录。

它会自动安排代码、控制分包大小并生成最终配置，无需维护 `app.json.subPackages`。

在需要按需加载的位置使用 JavaScript 动态 `import()` 即可。React 组件可以使用 `React.lazy(() => import('./features/report'))`。

## 优势

:::note[模块自由引用]
模块之间可以自由引用，无论引用方和依赖最终位于主包、同一分包还是不同分包，都不需要修改导入方式或关心跨包方向。
:::

### 像标准 Web 应用一样组织模块

业务代码继续使用标准 ESM 的 `import` 与 `import()`。vpt全自动分包会尽可能保持标准 Web 的模块行为，让模块引用不受最终物理目录影响：

- **微信主包到分包**：动态 `import()` 会在需要时自动加载对应代码分包。
- **分包到主包**：分包代码可以直接复用已经位于主包的模块。
- **分包到分包**：一个代码分包可以引用另一个代码分包中的模块，vpt全自动分包会自动完成加载与连接。

应用代码不需要遵循微信原生分包之间的引用方向来安排源码，也不需要为了规避兄弟分包限制而复制共享模块、创建中转文件或修改导入路径。你只需要用静态 `import` 表达同步依赖，用动态 `import()` 表达按需加载；vpt全自动分包会负责合法的物理放置与加载顺序。

### 分包位置对业务代码透明

模块最终位于主包还是哪个代码分包，不会出现在业务导入路径中。调整功能大小、增加动态入口或重新构建后，生成的分包布局可以变化，而源码仍保持普通 Web 项目的组织方式。

静态依赖、共享模块和循环引用仍按原始 ESM 关系连接。它只改变代码如何被微信下载，不改变应用如何声明和使用模块。

### 共享依赖不会重复打包

[旧版 Taro 的“智能提取分包依赖”方案](https://docs.taro.zone/docs/mini-split-chunks-plugin)会把多个分包共同使用的模块提取为 `sub-common`。由于微信原生分包不能跨分包引入文件，这些模块需要复制到每个相关分包，Taro 文档也明确提示这会增大整体包体积。

vpt全自动分包为每个模块确定唯一归属，不再需要为了满足分包引用限制而复制依赖。

## 最小示例

静态导入会让模块进入首屏同步依赖图：

```ts
import { createReport } from './features/report'

createReport()
```

改为动态导入后，该功能及其专属依赖就可以进入自动生成的代码分包：

```ts
async function openReport() {
    const { createReport } = await import('./features/report')
    return await createReport()
}
```

调用 `openReport()` 时，微信运行时才会下载并执行对应的分包代码。代码仍然使用普通 ESM 导入，不需要调用微信分包 API，也不需要写平台专用路径。

React 组件可以直接使用 `lazy()` 创建相同的动态导入边界：

```tsx
import { lazy, Suspense } from 'react'
import { View } from 'virtual:taro/components'

const Report = lazy(() => import('./features/report'))

function ReportEntry() {
    return (
        <Suspense fallback={<View>正在加载报表…</View>}>
            <Report />
        </Suspense>
    )
}
```

`./features/report` 需要默认导出 React 组件。首次渲染 `<Report />` 时，对应代码分包才会被加载。

## 哪些代码会进入主包

规划器首先确定不能异步移动的代码。以下模块始终留在主包：

- App、Page 和 Component 的原生入口。
- 对应的应用入口模块及其全部静态依赖。
- 被首屏同步代码静态引用的共享模块。

主包所有权优先。例如，一个工具模块同时被首页和懒加载功能使用时，它只会保留在主包，不会复制到分包：

```text
首页 ──静态导入──▶ shared.ts ◀──静态导入── 懒加载功能
                     │
                     └── 主包中只保留一份
```

vpt全自动分包不会把已有的静态依赖偷偷改成异步依赖。如果主包过大，需要由应用代码添加合理的 `import()` 边界。

## 哪些代码可以进入分包

只有满足下面条件的 JavaScript 模块才会成为分包候选：

1. 模块位于一个真实的动态 `import()` 边界之后。
2. 从 App 或任何已配置页面的同步依赖图无法到达该模块。
3. 模块没有因为与同步代码共享而被主包优先保留。

规划器从每个动态导入目标开始，只沿静态导入继续遍历。遇到新的动态导入时，会把它视为下一条独立的延迟加载边界。

```text
页面与 App
│
├── 静态依赖 ─────────────────────▶ 主包
│
└── import('./feature-a')
    ├── feature-a.ts ─────────────▶ 分包候选
    ├── feature-a-helper.ts ──────▶ 分包候选
    └── import('./feature-b') ────▶ 新的延迟加载边界
```

## 分包策略

应用通过静态 `import` 和动态 `import()` 控制模块的加载时机，vpt全自动分包再根据这些边界决定模块归属和物理分包。你控制的是同步或按需加载关系，不需要指定分包名称、目录或大小。

### 让模块留在主包

从 App、页面或它们的同步依赖中静态导入模块，该模块就会留在主包：

```ts
import { initializeSession } from './session'

initializeSession()
```

只要存在一条从同步入口到该模块的静态引用路径，主包所有权就会优先。延迟功能也可以直接复用这个模块，不会生成副本。

### 让功能按需进入分包

确保功能只能通过动态 `import()` 到达。该功能静态导入的专属依赖会一起成为分包候选：

```ts
async function openEditor() {
    const { mountEditor } = await import('./features/editor')
    return mountEditor()
}
```

适合延迟加载的边界通常是低频页面、大型编辑器、图表、报表、导出工具或仅在特定操作后使用的功能。不要为了拆包而逐个动态导入很小的工具模块，应围绕完整业务功能创建边界。

### 创建多级加载边界

延迟功能内部可以继续使用动态导入，形成下一阶段的按需加载：

```ts
// features/report.ts
export async function exportReport() {
    const { exportToPdf } = await import('./report-pdf')
    return exportToPdf()
}
```

`report` 和 `report-pdf` 是两个独立的逻辑加载阶段。规划器可能根据大小把它们放在同一物理分包或不同分包；`report-pdf` 的导入与执行只会在调用 `exportReport()` 后发生。

### 避免意外进入主包

如果一个本应延迟加载的模块同时被同步代码静态导入，它会回到主包。检查公共入口文件和聚合导出，避免从同步路径重新导出大型功能：

```ts
// 不要在同步入口中重新导出延迟功能
export { mountEditor } from './features/editor'
```

仅用于 TypeScript 类型的依赖应使用 `import type`。类型导入会在构建时移除，不会影响模块归属：

```ts
import type { EditorOptions } from './features/editor'
```

### 物理分包由 vpt 管理

vpt 不提供手动指定 `package`、分包根目录或模块清单的选项。一个动态导入边界也不保证对应一个物理分包；规划器可以合并较小的延迟功能，也可以把过大的延迟依赖图拆到多个分包。

这种分工让应用只表达标准模块关系和加载时机，同时由 vpt 负责满足微信的分包大小与引用要求。构建后可以检查 `dist/wx/app.json` 和 `dist/wx/sub`，确认最终布局是否符合预期。

## 如何规划分包

模块图分析完成后，规划器使用确定性的 best-fit decreasing 策略打包候选模块：

1. 按转换后源码的估算体积从大到小处理模块。
2. 优先放入仍有足够空间且剩余空间最小的现有分包，以减少分包数量。
3. 空间相同时，优先把属于同一动态入口或具有直接静态依赖关系的模块放在一起。
4. 没有现有分包可容纳模块时，创建新的代码分包。

每个分包的规划预算为 **1,900,000 字节**，为模块包装、加载器和构建生成代码预留微信 2 M 限制内的空间。

:::caution
规划预算使用转换后源码大小进行估算，不等于微信开发者工具最终统计的上传体积。生产发布前仍应使用微信开发者工具或 CI 检查最终主包、分包和整个项目的大小。
:::

## 稳定且可复现的输出

每个生成分包的目录名来自其模块 ID 集合的稳定哈希：

```text
dist/wx/
├── app.json
├── assets/
└── sub/
    ├── p_2f8a91c4/
    │   └── assets/
    │       └── <content-hash>.js
    └── p_b14e638a/
        └── assets/
            └── <content-hash>.js
```

相同模块图会得到相同的 `p_<8位哈希>` 根目录，不受模块遍历顺序影响。被 tree shaking 删除的代码不会留下空分包。

构建时会把最终仍有输出代码的分包写入 `app.json`：

```json
{
    "pages": ["pages/index/index"],
    "subPackages": [
        {
            "name": "p_2f8a91c4",
            "root": "sub/p_2f8a91c4",
            "pages": []
        }
    ]
}
```

这些分包是只存放 JavaScript 的代码分包，因此 `pages` 为空。页面仍由 `vitePluginTaro({ pages: [...] })` 统一配置。

:::caution
不要在 `appJson` 中手动配置 `subPackages` 或 `subpackages`。vpt全自动分包会移除这两个字段，并根据当前模块图生成最终声明。
:::

## 运行时如何加载

主包中包含一个由构建结果生成的传输表。加载方式取决于代码的物理位置：

| 代码位置 | 微信加载方式 |
| --- | --- |
| 主包 | 同步 `require()` |
| 自动生成的代码分包 | 异步 `require.async()` |

加载流程如下：

```text
应用调用 import()
    ↓
SystemJS 请求模块注册
    ↓
主包传输表定位物理文件
    ↓
require.async() 下载对应微信分包
    ↓
SystemJS 链接原始 ESM 依赖图并执行模块
```

逻辑模块 ID 与物理分包路径相互独立。即使一个延迟加载图因为体积被拆到多个分包，SystemJS 仍会按照原始 ESM 图处理静态依赖、循环依赖和执行顺序，应用代码不需要知道模块最终位于哪个分包。

异步分包加载依赖微信的 `require.async()`，因此基础库版本需要为 **2.11.2 或更高版本**。

## 样式和资源

当前自动规划对象是 JavaScript 模块：

- 全局样式仍输出到主包的 `app.wxss`。
- 图片、字体和其他通用构建资源仍由主包管理。
- 构建不会在兄弟分包之间生成资源引用。

因此，把大型 JavaScript 功能改为动态导入可以减少主包代码，但不会自动把该功能引用的所有非 JavaScript 资源一起移动到代码分包。

## 设计原则

vpt全自动分包遵循以下原则：

- **标准语法**：以 `import()` 表达延迟加载，不引入专用配置 DSL。
- **主包优先**：同步依赖永远不会为了减小主包而被擅自异步化。
- **不重复模块**：一个逻辑模块只属于主包或一个生成分包。
- **确定性输出**：相同模块图生成相同分包根目录。
- **物理位置透明**：业务代码不依赖 `sub/p_*` 路径。
- **只影响微信**：不会改变 H5 的 Vite 构建行为。
